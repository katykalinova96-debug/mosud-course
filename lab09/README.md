## 1. Исходное отношение и функциональные зависимости

Исходное отношение:

`delivery_flat(shipment_id, order_id, seller_id, seller_city, attempt_no, attempt_time, event_code, event_name)`.

По бизнес-правилам варианта определены функциональные зависимости:

1. `shipment_id → order_id, seller_id` — отправление определяет заказ и продавца.
2. `seller_id → seller_city` — продавец определяет свой город.
3. `event_code → event_name` — код события определяет его название.
4. `(shipment_id, attempt_no) → attempt_time` — номер попытки в пределах отправления определяет время попытки.

## 2. Потенциальный ключ и замыкание

Проверено замыкание набора `{shipment_id, attempt_no, event_code}`:

- Начальные атрибуты: `{shipment_id, attempt_no, event_code}`.
- По зависимости `shipment_id → order_id, seller_id` получаем `order_id, seller_id`.
- По `seller_id → seller_city` получаем `seller_city`.
- По `(shipment_id, attempt_no) → attempt_time` получаем `attempt_time`.
- По `event_code → event_name` получаем `event_name`.

В замыкании содержатся все восемь атрибутов отношения. Ни один из трёх исходных атрибутов ключа не выводится из остальных по заданным зависимостям. Поэтому **`(shipment_id, attempt_no, event_code)` — потенциальный ключ**.

Предполагается, что для одной попытки доставки каждый код события регистрируется не более одного раза. Для хранения нескольких одинаковых событий одной попытки потребовался бы отдельный идентификатор события, отсутствующий в исходном задании.

## 3. Частичные и транзитивные зависимости

От составного ключа существуют частичные зависимости: `shipment_id → order_id, seller_id`, `(shipment_id, attempt_no) → attempt_time`, `event_code → event_name`. Из-за них исходное отношение не соответствует 2НФ.

Транзитивная зависимость: `shipment_id → seller_id → seller_city`. Город продавца в плоской таблице повторяется для разных отправлений одного продавца.

## 4. Аномалии плоской таблицы

- **INSERT:** для добавления нового типа события без существующей попытки доставки нужно было бы создавать неполную строку плоской таблицы.
- **UPDATE:** при изменении названия события пришлось бы обновлять все строки с соответствующим `event_code`; неполное обновление привело бы к противоречию.
- **DELETE:** при удалении последней строки с конкретным `event_code` терялось бы название этого типа события.

## 5. Последовательная декомпозиция до 3НФ

**Исходная таблица:** `delivery_flat` с составным ключом `(shipment_id, attempt_no, event_code)`.

**Переход к 2НФ:** для устранения частичных зависимостей выделены:

- `shipments_2nf(shipment_id, order_id, seller_id, seller_city)` — зависимость от `shipment_id` (включая транзитивно определяемый город).
- `attempts(shipment_id, attempt_no, attempt_time)` — зависимость `(shipment_id, attempt_no) → attempt_time`.
- `event_types(event_code, event_name)` — зависимость `event_code → event_name`.
- `attempt_events(shipment_id, attempt_no, event_code)` — связь попыток и типов событий.

**Переход к 3НФ:** устранена транзитивная зависимость `shipment_id → seller_id → seller_city`: таблица `shipments_2nf` разделена на `nf_6_shipments(shipment_id, order_id, seller_id)` и `nf_6_sellers(seller_id, seller_city)`.

Итоговые отношения в PostgreSQL:

| Таблица | Первичный ключ | Назначение |
|---|---|---|
| `lab.nf_6_sellers` | `seller_id` | Город продавца |
| `lab.nf_6_shipments` | `shipment_id` | Заказ и продавец отправления |
| `lab.nf_6_attempts` | `(shipment_id, attempt_no)` | Время попытки доставки |

## 6. Проверка НФБК и сохранения зависимостей

В каждом итоговом отношении детерминант нетривиальной функциональной зависимости является его ключом. Следовательно, итоговая схема соответствует **НФБК (BCNF)** и тем самым 3НФ. Все четыре заданные функциональные зависимости сохраняются локально в отдельных таблицах.

Декомпозиция без потерь: общие атрибуты при каждом разбиении образуют ключ выделяемого справочника или дочернего отношения. В SQL дополнительно предусмотрена проверка исходных плоских строк и результата обратного соединения через `EXCEPT` в обе стороны.

Созданы пять таблиц с именами `lab.nf_6_*`, первичными и внешними ключами, ограничениями `UNIQUE` и `CHECK`. Для тестирования используются настоящие идентификаторы заказов и продавцов из Olist. ## 8. Контрольные вопросы

**1. Что означает замыкание множества атрибутов?**  
Это все атрибуты, которые можно функционально определить из заданного множества с использованием функциональных зависимостей.

**2. Чем 3НФ отличается от НФБК?**  
НФБК строже: в каждой нетривиальной функциональной зависимости детерминант должен быть суперключом. В 3НФ возможны исключения, когда зависимый атрибут является частью потенциального ключа.

**3. Что значит «декомпозиция без потерь»?**  
Это разбиение таблицы, при котором естественное соединение итоговых отношений восстанавливает исходные данные без потери строк и появления ложных комбинаций.
