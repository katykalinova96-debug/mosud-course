## Реализованная модель

Созданы три таблицы схемы `lab`:

- `shipments` — отправления по заказам и продавцам;
- `delivery_attempts` — последовательные попытки доставки отправлений;
- `delivery_events` — события, связанные с попытками доставки.

Таблица `shipments` связана внешними ключами с `olist.orders` и `olist.sellers`. Таблица `delivery_attempts` связана с `olist.orders` и составным внешним ключом с `lab.shipments`. Таблица `delivery_events` связана составным внешним ключом с `lab.delivery_attempts`. Связи между отправлениями, попытками и событиями имеют кратность 1:N; дочерняя запись обязательно ссылается на родительскую, а родительская может не иметь дочерних записей.

## Бизнес-правила и ограничения

| № | Правило | Ограничение |
|---|---|---|
| 1 | Каждое отправление связано с существующим заказом. | `fk_shipments_order` |
| 2 | Каждое отправление связано с существующим продавцом. | `fk_shipments_seller` |
| 3 | Код отслеживания уникален. | `uq_shipments_tracking_code` |
| 4 | Для одной пары «заказ — продавец» существует не более одного отправления. | `uq_shipments_order_seller` |
| 5 | Статус отправления принимает только предусмотренные значения. | `ck_shipments_status` |
| 6 | Дата доставки не может предшествовать созданию отправления. | `ck_shipments_delivery_time` |
| 7 | Статус `delivered` требует заполненной даты доставки. | `ck_shipments_delivered_date` |
| 8 | Номер попытки положительный и уникален внутри отправления. | `ck_attempts_number`, `uq_attempts_shipment_number` |
| 9 | Попытка ссылается на отправление и тот же заказ; результат попытки ограничен списком значений. | `fk_attempts_shipment_order`, `ck_attempts_result` |
| 10 | Событие связано с существующей попыткой того же отправления; тип события ограничен списком значений. | `fk_events_attempt_shipment`, `ck_events_type` |

Во всех трёх таблицах заданы первичные ключи `pk_...` и обязательные поля `NOT NULL`. Дополнительные составные `UNIQUE` используются как целевые ключи для составных внешних ключей.

## Контрольные вопросы

**1. Когда для связи M:N нужна отдельная таблица?**  
Если нескольким записям первой сущности могут соответствовать несколько записей второй, используется связующая таблица с внешними ключами на обе сущности.

**2. Чем естественный ключ отличается от surrogate key?**  
Естественный ключ формируется из предметных данных (например, `tracking_code`), а суррогатный — искусственный идентификатор (`shipment_id`).

**3. Какие ограничения следует задавать декларативно?**  
`PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL` и `CHECK`, если правило можно выразить через ограничения таблицы. Триггеры нужны для правил, зависящих от нескольких изменяемых строк или сложных условий.
