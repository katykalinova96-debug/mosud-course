## Цель работы

Исследовать конкурентный доступ к данным в PostgreSQL, сравнить уровни изоляции транзакций и проверить способы безопасного изменения остатков товаров.

## Подготовка данных

В `lab12.sql` созданы таблицы:

- `lab.inventory` — остатки (`product_id`, `qty`, `version`), внешний ключ на `olist.products` и ограничение `qty >= 0`;
- `lab.inventory_movements` — журнал движений (`movement_id`, `product_id`, `qty_delta`, `created_at`);
- `lab.lab12_targets` — соответствие обозначений `P1` и `P2` реальным идентификаторам товаров Olist.

Добавлено 100 товаров с начальным остатком 10 единиц. Тестовый атомарный `UPDATE` изменил остаток P1 с 10 до 9, после `ROLLBACK` остаток вернулся к 10. Для экспериментов открыты два независимых сеанса PostgreSQL: A (`pg_backend_pid() = 163`) и B (`pg_backend_pid() = 170`).

Файлы `session_a.sql` и `session_b.sql` содержат команды обоих сеансов с отметками очередности. Выполнять их нужно **поэтапно**, а не запускать целиком.

## Результаты экспериментов

| Эксперимент | Уровень изоляции | Наблюдаемый эффект | Способ предотвращения / пояснение |
|---|---|---|---|
| Потерянное обновление | READ COMMITTED | Оба сеанса прочитали `qty = 10` и записали константу `9`. Итог — `9` вместо `8`. | Атомарный `UPDATE`, `SELECT ... FOR UPDATE` или контроль версии. |
| Блокировка строки | READ COMMITTED | B ожидал снятия блокировки A; после фиксации A получил `9`. После второго списания итог `8`. | `SELECT ... FOR UPDATE` перед изменением строки. |
| Атомарное резервирование | READ COMMITTED | Два последовательных списания: `10 → 9 → 8`. | `UPDATE ... SET qty = qty - 1 WHERE qty > 0 RETURNING qty`. |
| Неповторяемое чтение | READ COMMITTED | В A первое чтение `10`, после `COMMIT` B повторное чтение `7`. | `REPEATABLE READ` для неизменного снимка. |
| Повторяемое чтение | REPEATABLE READ | В A оба чтения дали `10`, хотя B установил `7`. После завершения транзакции A стало видно `7`. | Снимок данных сохраняется в рамках транзакции. |
| Фантомное чтение | READ COMMITTED | `COUNT(*)` по `qty_delta < 0` в A изменился с `0` на `1` после вставки B. | `REPEATABLE READ` сохраняет согласованный снимок данных. |
| Взаимная блокировка | READ COMMITTED | A удерживал P1 и ждал P2; B удерживал P2 и ждал P1. PostgreSQL выдал `ERROR: deadlock detected` в B. | Захватывать ресурсы в едином порядке, повторять прерванные транзакции. |
| Конфликт сериализации (доп.) | SERIALIZABLE | B получил `could not serialize access due to concurrent update`. После `ROLLBACK` и повторного выполнения транзакции итог P1: `qty = 8`, `version = 2`. | Повторять всю транзакцию при `serialization_failure` (SQLSTATE `40001`). |

Все результаты получены при выполнении команд в двух независимых сеансах PostgreSQL. Ошибки deadlock и serialization_failure были ожидаемыми результатами соответствующих экспериментов.

## Пояснения к экспериментам

**Потерянное обновление.** Если оба сеанса читают `10` и затем записывают заранее вычисленную константу `9`, одно из двух списаний не учитывается. При арифметическом обновлении `qty = qty - 1` сервер применяет изменение к актуальному значению после получения блокировки.

**Блокировка строки.** Команда `SELECT ... FOR UPDATE` удерживает блокировку выбранной строки до завершения транзакции. Второй сеанс ждёт, затем читает уже зафиксированный результат первой транзакции.

**Уровни изоляции.** В `READ COMMITTED` каждый новый SQL-оператор видит новый снимок зафиксированных данных, поэтому возможно неповторяемое и фантомное чтение. В `REPEATABLE READ` используется один снимок данных для транзакции.

**Взаимная блокировка.** Сеанс A удерживал P1 и запрашивал P2, а B удерживал P2 и запрашивал P1. PostgreSQL обнаружил цикл ожидания, отменил транзакцию B; в ней выполнен `ROLLBACK`, в A — `COMMIT`.

**SERIALIZABLE.** Оба сеанса прочитали P1 со значением 10. После изменения P1 и `COMMIT` в A транзакция B не смогла изменить ту же строку, поскольку работала со старым снимком. После `ROLLBACK` и повторного выполнения транзакции B результатом стало `qty = 8`.

## Восстановление исходного состояния

После экспериментов остатки P1 и P2 восстановлены до `qty = 10`, `version = 0` (`UPDATE 2`). Тестовая запись в журнале удалена (`DELETE 1`). Проверка `SELECT COUNT(*) FROM lab.inventory WHERE qty < 0` вернула `0`.

| Товар | `qty` после восстановления | `version` |
|---|---:|---:|
| P1 | 10 | 0 |

## Контрольные вопросы

**1. Почему READ UNCOMMITTED в PostgreSQL не даёт грязного чтения?**  
В PostgreSQL `READ UNCOMMITTED` фактически работает как `READ COMMITTED`: незавершённые изменения других транзакций не видны благодаря MVCC.

**2. Чем SELECT ... FOR UPDATE отличается от обычного SELECT?**  
Обычный `SELECT` читает доступную версию строки и сам по себе не блокирует её для записи другими транзакциями. `SELECT ... FOR UPDATE` блокирует выбранные строки от конкурирующих изменений до завершения транзакции.

**3. Почему UPDATE qty = qty - 1 безопаснее схемы read-modify-write с константой?**  
При `UPDATE qty = qty - 1` PostgreSQL выполняет арифметическое изменение под блокировкой строки, а конкурирующий запрос ждёт и применяет изменение к актуальному остатку. При записи заранее вычисленной константы можно потерять одно из обновлений.
