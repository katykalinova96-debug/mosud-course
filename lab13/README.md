## Цель

Исследовать влияние B-tree индекса на план выполнения запроса к таблице `olist.products`, сравнить составной и частичный индексы, проверить поведение при низкой селективности.

## Исходные данные и запрос

Используется таблица `olist.products`. Фильтр содержит равенство `product_category_name = <выбранная категория>` и диапазон `product_weight_g BETWEEN 100 AND 500`. Скрипт выбирает категорию по реальным данным: 5–500 товаров в выбранном диапазоне веса. Поэтому категория и число строк определяются при запуске, а не задаются заранее.

В составном B-tree индексе порядок `(product_category_name, product_weight_g)` выбран потому, что по категории выполняется проверка на равенство, а по весу — диапазонный поиск. Такой порядок позволяет ограничивать диапазон поиска внутри выбранной категории.

## Эксперимент

Последовательность: проверить существующие индексы → получить исходный план `EXPLAIN (ANALYZE, BUFFERS)` → создать составной B-tree → `ANALYZE` → повторить план → проверить низкоселективный предикат → определить размер → создать частичный индекс → проверить план и размер → удалить оба тестовых индекса.

Второй индекс — частичный индекс по `product_weight_g`, содержащий только строки одной выбранной категории. Он хранит меньше записей, чем индекс по всей таблице, но полезен только для запросов, условие которых подразумевает его предикат.

### Низкоселективный запрос

Запрос с условиями `product_category_name IS NOT NULL AND product_weight_g > 0` вернул **32 945 из 32 951** строк. PostgreSQL выбрал **`Seq Scan`**, несмотря на наличие индекса. Показатели: `Execution Time = 5,634 мс`, `Buffers: shared hit=437`, `actual rows=32945`. Последовательное сканирование оказалось рациональным для условия, которому удовлетворяет почти вся таблица.

## Вывод

Составной B-tree индекс по `(product_category_name, product_weight_g)` ускорил выборку товаров заданной категории и диапазона веса примерно в **6,6 раза** в одном экспериментальном запуске. Для низкоселективного запроса PostgreSQL сохранил последовательное сканирование. Частичный индекс оказался значительно компактнее, но не обеспечил дополнительного ускорения в этом измерении.

Таким образом, выбор индекса зависит от условий запроса, селективности и затрат на чтение данных. Поскольку значения времени получены при отдельных запусках, для устойчивой оценки производительности требуются повторные измерения. Все тестовые индексы удалены после эксперимента.

## Контрольные вопросы

**1. Почему индекс может не использоваться даже при наличии подходящего столбца?**  
Планировщик оценивает стоимость выполнения. Если условие выбирает большую часть таблицы, последовательное чтение может быть дешевле индексного доступа и последующих обращений к строкам таблицы.

**2. Как порядок столбцов влияет на составной B-tree индекс?**  
Поиск эффективнее, когда ограничения запроса соответствуют ведущим столбцам индекса. В данном случае равенство по категории перед диапазоном по весу позволяет ограничить участок индекса, который нужно просмотреть.

**3. Когда полезен частичный индекс?**  
Когда запросы часто обращаются к определённому подмножеству строк, которое можно задать предикатом. Частичный индекс может быть меньше полного, но применяется только если условие запроса соответствует условию индекса.
