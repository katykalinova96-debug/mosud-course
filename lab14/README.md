# Практическая работа № 14. EXPLAIN ANALYZE и оптимизация запросов

**Вариант:** 6 — фильтр после `LEFT JOIN`.

**Цель:** сравнить исходный и переписанный запросы с помощью `EXPLAIN (ANALYZE, BUFFERS)`, проверить равенство результатов и объяснить изменение плана.

## Исходные данные и задача

Использованы таблицы `olist.orders`, `olist.customers`, `olist.order_items` базы Olist. Рассматриваются доставленные заказы клиентов штата RJ. Для каждого заказа рассчитываются количество позиций стоимостью от 500 BRL и их суммарная стоимость с доставкой. Заказы без дорогих позиций должны присутствовать с нулевыми показателями.

## Исходная и оптимизированная формы

В исходном запросе сначала выполняется `LEFT JOIN` всех позиций заказа, затем условие `oi.price >= 500` применяется внутри агрегатных функций (`FILTER`). В результате промежуточное соединение включает и ненужные для расчёта позиции.

В переписанном запросе условие цены перенесено в `ON` соединения с `order_items`. Поэтому в агрегирование передаются только подходящие позиции, а `LEFT JOIN` сохраняет все выбранные заказы. Для них применяются `COUNT` и `COALESCE(SUM(...), 0)`.

Простая замена `WHERE oi.price >= 500` на условие `ON` **не сохраняет результат**: фильтрация в `WHERE` исключает заказы без дорогих позиций, тогда как `LEFT JOIN` с условием в `ON` их сохраняет. Поэтому для доказуемой эквивалентности исходный запрос использует условную агрегацию, а не отбрасывание строк в `WHERE`.

Изменение соответствует **проталкиванию выборки к соединению**: фильтрация правого отношения выполняется до агрегации, уменьшая число промежуточных строк.

## Результаты эксперимента

На базе Olist найдено 12 350 доставленных заказов клиентов штата RJ. Дорогими считаются товарные позиции с `price >= 500` BRL.

| Показатель | Исходный запрос | Переписанный запрос |
|---|---:|---:|
| Execution Time, мс | 116,009 | 64,858 |
| Основной узел соединения | Parallel Hash Right Join | Parallel Hash Right Join |
| Estimated rows узла JOIN (на проход) | 8 299 | 7 326 |
| Actual rows узла JOIN (на проход, в среднем) | 7 072 | 6 182 |
| Shared buffers, hit / read (весь план) | 3 330 / 2 397 | 5 727 / 0 |
| Промежуточных строк `LEFT JOIN` | 14 143 | 12 364 |
| Заказов в результате | 12 350 | 12 350 |
| Дорогих позиций | 391 | 391 |
| Суммарная стоимость дорогих позиций с доставкой, BRL | 401 017,84 | 401 017,84 |

Указанные для параллельного соединения `estimated rows` и `actual rows` относятся к **одному проходу узла** (`loops=2`), поэтому они не равны общему числу строк соединения. В исходном плане `Parallel Seq Scan` таблицы `order_items` читает позиции без ограничения цены (`actual time` до 67,030 мс на проход), а в переписанном применяет `Filter: price >= 500` до соединения (`actual time` до 8,594 мс). Число подходящих позиций этого сканирования составляет в среднем 1 620 строк на проход вместо 56 325 строк до фильтрации. При этом на сканирование прочитано 2 397 буферов в первом запуске и использовано 2 397 уже кэшированных буферов во втором.

В данном измерении время выполнения сократилось на **51,151 мс** (примерно **в 1,79 раза**), а промежуточный результат `LEFT JOIN` уменьшился на **1 779 строк** (около **12,6%**). При сравнении времени необходимо учитывать, что первый запуск читал страницы с диска (`shared read=2397`), а второй выполнялся преимущественно из кэша: одиночное измерение не позволяет приписать всё ускорение только изменению SQL.

**Проверка эквивалентности:**

| Направление `EXCEPT` | Количество различий |
|---|---:|
| `before_minus_after` | 0 |
| `after_minus_before` | 0 |

Отдельная проверка семантики показала: если использовать `WHERE oi.price >= 500`, в результате останется **377** заказов, а при переносе условия в `ON` с сохранением `LEFT JOIN` — **12 350**. Поэтому эти два варианта напрямую не эквивалентны; в исходной эквивалентной форме используется условная агрегация `FILTER`.

**Вывод:** перенос фильтра `oi.price >= 500` в `ON` сократил количество строк, передаваемых в соединение и агрегирование, при сохранении всех доставленных заказов выбранного штата и тех же вычисленных сумм. Эквивалентность подтверждена двумя проверками `EXCEPT` без различий. План по-прежнему использует последовательное чтение `order_items`, поскольку для получения подходящих строк требуется просмотреть таблицу; выигрыш достигается прежде всего за счёт ранней фильтрации и уменьшения дальнейшей обработки. Также на измерение времени повлияло состояние кэша PostgreSQL.


## Контрольные вопросы

**1. Почему уменьшение промежуточного отношения может ускорить JOIN?**

СУБД обрабатывает меньше строк, выполняет меньше сравнений и передаёт меньше данных в последующие операции, например группировку или сортировку.

**2. Что означает большое расхождение estimated rows и actual rows?**

Это означает, что оценка количества строк планировщиком неточна. Из-за этого он может выбрать неоптимальный порядок соединений или метод доступа.

**3. Почему оптимизированный запрос необходимо проверять на эквивалентность результата?**

Переписывание SQL может изменить состав строк и значения агрегатов. Проверка через `EXCEPT` в обе стороны позволяет обнаружить различия и подтвердить сохранение результата на проверяемых данных.
